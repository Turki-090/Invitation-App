# Authentica sign-in code activation plan

Host sign-in is a phone one-time code. Supabase Auth issues the session, and
[Authentica](https://authentica.sa) delivers the code to the handset over
WhatsApp, with SMS behind it. This is the plan to take that path from the inert
local placeholder to real delivery.

The application code is finished. What remains is an Authentica account, a
Supabase hook configuration, and the staging exercise that proves a real phone
receives a real code.

The vendor's own API blueprint is checked in at
[`../vendor/authenticasa.apib`](../vendor/authenticasa.apib) — it is Authentica's
reference, not a contract this platform serves, and `openapi/openapi.yaml`
remains the only source for our own transport contract.

## Why Authentica does not verify the code

Authentica can both send and verify a code, and the platform uses only the
sending half. The code is generated by Supabase Auth, delivered by Authentica,
and verified by Supabase Auth.

Splitting it the other way — letting Authentica verify — would create a second
answer to "is this person signed in", which the API's bearer-token model cannot
express, and would make a delivery outage capable of minting sessions. Delivery
is a channel concern; identity is not. A vendor change on the delivery side
never touches session issuance, the `User.authProviderId` mapping, or any
client.

## How a sign-in flows

```
web  ──signInWithOtp(phone)──▶  Supabase Auth
                                     │ generates the six-digit code
                                     ▼
                        POST /api/v1/webhooks/supabase-otp
                                     │ Standard Webhooks signature
                                     ▼
                        API verifies the signature, then forwards
                                     ▼
                          Authentica  POST /send-otp  (custom `otp`)
                                     ▼
                              WhatsApp, SMS fallback

web  ──verifyOtp(phone, code)──▶  Supabase Auth  ──▶  access token  ──▶  API
```

The API never generates, stores, or logs the code. It forwards a code it has
just authenticated as Supabase's.

## Phase 0 — Authentica account

| Asset                  | What it is                         | Notes                                                           |
| ---------------------- | ---------------------------------- | --------------------------------------------------------------- |
| Authentica account     | The portal at portal.authentica.sa | Saudi provider; billing is per delivered message                |
| API key                | `X-Authorization` credential       | Generated under the portal's API keys settings                  |
| Application settings   | Default channel and fallback       | Set the fallback channel to SMS so WhatsApp failures still land |
| Balance                | Prepaid message credits            | An exhausted balance fails sign-in for everyone at once         |
| Sender name (SMS only) | Registered alphanumeric sender     | Optional; the Authentica default sender works without one       |

Set the Authentica application's fallback channel to SMS. The hook always sends
`fallback_phone`, so the fallback needs no further configuration. Leave an email
fallback unset — the hook carries a phone number and nothing else, which is why
`AUTHENTICA_OTP_METHOD` accepts only `whatsapp` and `sms`.

## Phase 1 — Templates

Authentica templates are per channel, and the template has to match the channel
in use. `AUTHENTICA_OTP_TEMPLATE_ID` defaults to `1`, the Arabic default
template; `2` is its English counterpart. Those two are also what Authentica
uses for the fallback message.

Pick the template in the Authentica dashboard, confirm it is a WhatsApp template
when `AUTHENTICA_OTP_METHOD` is `whatsapp`, and set its id in the environment. A
template belonging to a different channel is rejected at send time, which
surfaces as a failed sign-in rather than a failed deploy.

## Phase 2 — Supabase hook

1. In the Supabase dashboard, open Authentication → Hooks and add a **Send SMS
   hook** of type HTTPS.
2. Point it at `https://<api-host>/api/v1/webhooks/supabase-otp`.
3. Copy the generated secret. It looks like `v1,whsec_<base64>`; store it
   verbatim as `SUPABASE_SEND_SMS_HOOK_SECRET`, prefix included.
4. Enable Phone as a sign-in provider. No SMS provider credentials are needed —
   the hook replaces them.

The hook must be reachable from Supabase over the public internet, which is why
it stays disabled locally. To exercise it from a laptop, expose the API through
a tunnel and point a throwaway Supabase project at the tunnel URL.

## Phase 3 — Configuration

| Variable                        | Value                                                         |
| ------------------------------- | ------------------------------------------------------------- |
| `AUTHENTICA_OTP_ENABLED`        | `true`                                                        |
| `AUTHENTICA_API_KEY`            | The portal API key                                            |
| `SUPABASE_SEND_SMS_HOOK_SECRET` | The `v1,whsec_…` value from the hook, verbatim                |
| `AUTHENTICA_OTP_METHOD`         | `whatsapp`, or `sms`                                          |
| `AUTHENTICA_OTP_TEMPLATE_ID`    | A template id belonging to that channel                       |
| `AUTHENTICA_BASE_URL`           | `https://api.authentica.sa/api/v2` unless the vendor moves it |
| `AUTHENTICA_REQUEST_TIMEOUT_MS` | `10000`                                                       |

Startup validation refuses to boot an API that enables delivery without a usable
hook secret, without `SUPABASE_URL`, or — when deployed — with a placeholder API
key. A misconfiguration fails at deploy time rather than at the first host's
sign-in attempt.

## Phase 4 — Staging acceptance

Run against staging with a real Saudi number:

1. Request a code from the staging web sign-in. Confirm the WhatsApp message
   arrives and carries a six-digit code.
2. Enter it. Confirm the session is issued and the workspace loads.
3. Enter a wrong code. Confirm Supabase refuses it, and that no second message
   was sent.
4. Let a code expire, then request another. Confirm the newer code works.
5. Check the API logs for `auth.otp.delivered` with its channel, and confirm no
   log line anywhere contains the code or the phone number.
6. Temporarily set an invalid `AUTHENTICA_API_KEY`, request a code, and confirm
   the hook answers `502` with `auth.otp.delivery_failed` and
   `providerCode: PROVIDER_UNAUTHORIZED`. Restore the key afterwards.

## Failure modes

| Symptom                                           | Cause                                                   | Response                                                     |
| ------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------ |
| All sign-ins fail, `PROVIDER_UNAUTHORIZED`        | API key revoked, or rotated on one side only            | Rotate per the credential-rotation runbook                   |
| All sign-ins fail, `PROVIDER_BALANCE_EXHAUSTED`   | The Authentica prepaid balance is spent                 | Top up; watch the balance before it reaches zero             |
| Sign-ins fail, `auth.otp.hook_signature_rejected` | Hook secret mismatch, or clock skew beyond five minutes | Re-copy the secret verbatim; check host time synchronisation |
| Codes arrive by SMS instead of WhatsApp           | WhatsApp delivery failed and the fallback worked        | Expected; investigate only if it becomes the norm            |
| `503` with `auth.otp.delivery_not_configured`     | Delivery disabled, or the hook secret is missing        | Check `AUTHENTICA_OTP_ENABLED` and the hook secret           |

An Authentica outage appears as `auth.otp.delivery_failed` with a retryable
provider code. Supabase retries a `503` up to three times inside a five-second
budget, so brief provider blips are absorbed without the host noticing.
